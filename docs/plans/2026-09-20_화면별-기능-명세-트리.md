# 화면별 기능 명세 트리

- **이번에 비교하는 것**: 기능 명세 한 줄의 굵기. "ㅇㅇ페이지 ㅇㅇ기능"이라고 짚을 수 있을 만큼 잘게, 한눈에 들어올 만큼 짧게 — 아래 예시 형식이 그 균형에 맞는지.
- **이번 승인으로 바뀌는 것**: `docs/specs/화면/`에 화면당 파일 하나씩 명세가 생긴다. 형식이 확정된 뒤에 개발 서버 전용 플로팅 버튼이 지금 경로의 명세를 띄운다.
- **바뀌지 않는 것**: 화면 동작, 라우트, 저장 데이터, production 빌드(버튼은 dev에서만), 기존 `UX·화면 명세`(설계 문서로 그대로 둠), `원칙.md`.

출처: 주간 노트 2026-W39 일요일 `아이디어`.

## 지금 상태

**사실** (코드 읽기로 확인)
- 라우트는 `window.location.pathname` 분기로 흩어져 있다. 제품 화면 7개: `/` 문장 보정, `/workspace/jamos` 자소 현황, `/workspace/jamo` 자소 편집, `/workspace/jamo/master` 원형, `/workspace/jamo/result` 조합별 결과, `/workspace/skeleton` 뼈대, `/workspace/review` 검수 격자. 랩 9개(`/grid-lab` `/rule-lab` `/font-guide-lab` 등).
- `docs/specs/KOREAN_FONT_MAKER_UX_SCREEN_SPEC.md`(1,211줄)는 "이렇게 만들자"는 설계다. 화면 ID(P-01, J-02…)가 있지만 지금 코드의 화면과 1:1이 아니다. 지금 있는 기능을 적은 문서는 없다.
- 자소 편집·검수 화면은 `레이아웃 수정을 자소 탭으로 옮기기`로 9/20에 바뀌었다(자소 탭 `획 · 레이아웃` 전환, 검수는 격자만, 미커밋 · G3 대기). G0 명세는 이 상태를 기준으로 쓴다.

## 하려는 것

1. **명세는 지금 있는 것만 적는다.** 만들 것은 플랜에, 있는 것은 명세에. 폐기 예정 화면도 있는 그대로 적고 `폐기 예정`만 표시한다.
2. 화면당 파일 하나, `화면 → 영역 → 기능` 세 단. 기능은 한 줄: 무엇을 하는지 · 어디에 저장되는지. 기능마다 번호를 붙여 `자소편집 2.3`처럼 부른다.
3. `docs/specs/화면/_트리.md`에 전체 화면 목록과 서로 넘어가는 길을 한 장으로 둔다.
4. 형식이 G0에서 확정되면 dev 전용 플로팅 버튼을 붙인다. 파일 머리말의 `route`로 지금 경로의 명세를 찾아 그대로 보여 준다. 명세를 두 번 쓰지 않는다.
5. 화면을 고치는 플랜은 닫을 때 해당 명세 파일도 같이 고친다(진행 기록에 한 줄).

형식 예시(내용은 자리 표시, G0에서 실제로 채움):

```markdown
---
route: /workspace/jamo
name: 자소편집
status: 사용 중
---
# 자소 편집
문장 속 글자 하나를 골라 그 글자의 자소를 고친다.

## 1. 문장 줄
- 1.1 글자 고르기 — 누른 글자가 편집 대상이 된다 · 주소의 `char`
- 1.2 …

## 2. 편집 캔버스
- 2.1 획 앵커 옮기기 — … · 자모 스토어
```

## 게이트

| 게이트 | 닫는 조건 |
|---|---|
| D0 계약 | 둘 곳, 머리말 항목(`route` `name` `status`), 세 단 구조, 번호 규칙, "있는 것만 적는다" 확정. |
| G0 대표 | 자소 편집 · 검수 격자 두 화면을 코드 기준으로 작성. 사용자가 읽고 **한 줄의 굵기**를 판정(너무 잘다 / 맞다 / 너무 굵다). 판단 변수는 이것 하나. |
| G1 홀드아웃 | 성격이 다른 화면 둘(문장 보정, 랩 하나)을 같은 형식으로 작성. 형식을 안 고치고 들어가는지 본다. |
| G2 전수 | 범위 안 모든 화면 작성 + `_트리.md`. 라우트 목록과 명세 파일의 `route`가 1:1인지 보는 테스트 추가, `npm test` 통과. 플로팅 버튼 구현, production 빌드에 안 들어감을 확인, Playwright로 토글 확인. |
| G3 사용자 검증 | 사용자가 트리만 보고 기능 셋을 번호로 짚어 대화가 되는지, 개발 화면에서 버튼으로 같은 내용이 뜨는지 판정. |

## 미결정 (승인 때 같이 답해 주세요)

1. **둘 곳** — 레포 `docs/specs/화면/`에 두고 볼트에 심볼릭 링크로 걸어 옵시디언에서 읽기(추천: 앱이 바로 읽고 문서 규칙 그대로) vs 옵시디언에 직접(규칙에 예외 추가, 앱이 읽으려면 복사 단계 필요).
2. **범위** — 제품 화면 7개 먼저(추천) vs 랩 9개까지. 랩은 G1에서 하나만 형식 확인용으로 쓴다.
3. **버튼이 보여 줄 것** — 지금 화면의 명세 전체(추천: 단순, 명세 그대로) vs 화면 한 줄 설명만.

## 이 플랜에 없는 것

- 기존 `UX·화면 명세` 정리나 화면 ID 통일.
- 흩어진 라우트 분기를 한 곳으로 모으는 리팩터(테스트에 필요한 목록 상수까지만).
- 화면 자체의 변경. 명세를 쓰다 발견한 문제는 옵시디언 `열린 질문`거리로만 알린다.
