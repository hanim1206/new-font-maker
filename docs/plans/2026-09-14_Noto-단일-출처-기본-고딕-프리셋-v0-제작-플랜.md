# Noto 단일 출처 기본 고딕 프리셋 v0 제작 플랜

## 한 줄 결론

기준선 자동 추출 완료를 기다리지 않는다. 현재 검증된 Noto Sans KR 자료와 동결한 레거시 값을 이용해 `기본 고딕 01`의 공간 구조 v0를 만들고, 사용자가 화면과 OTF를 확인한 뒤 보정한다.

단, 분석값은 제품 기본값으로 자동 승격하지 않는다. v0는 별도 후보로 만들고, 사용자 승인 후에만 배포 프리셋이 된다.

## 요구사항 요약

1. 배포 전 완성도 높은 고딕 프리셋 하나를 먼저 만든다.
2. 첫 버전은 Noto Sans KR Regular 한 종만 공간 구조 참고 자료로 사용한다.
3. 외부 폰트 윤곽을 복제하지 않는다. 현재 앱의 자모 형태를 유지한다.
4. 아직 없는 필드만 현재 앱 기본값으로 남기고 `current-fallback`으로 표시한다. 앱 기본값을 Noto 출처값처럼 쓰지 않는다.
5. 초성은 승인된 Noto v3 114건을 사용한다. 레거시는 비교·회귀 이력일 뿐 새 후보 입력으로 사용하지 않는다.
6. 이용제 분류는 생성 공식이 아니라 검수 표본을 나누는 기준으로만 사용한다.
7. 사용자 1차 확인 뒤 레이아웃을 보정하고, 레이아웃 승인 뒤에 자모 형태를 따로 보정한다.
8. 새 자동 추출값이 생겨도 기존 v0를 덮어쓰지 않는다. 새 후보와 차이표를 만든다.
9. 화면과 OTF는 같은 레이아웃·잉크 계산 경로를 사용한다.
10. 이후 여러 프리셋과 다중 폰트 중위값으로 확장할 수 있게 출처와 승인 상태를 남긴다.

## 이번 결정

### 제품 성격

- 사용자 노출명 후보: `기본 고딕 01`
- 내부 작업명: `neutral-gothic-noto-seed-v0`
- 목표: Noto 복제본이 아니라, Noto의 안정적인 공간 배치를 참고한 앱 고유 기본 고딕
- 굵기: Regular, 400 기준
- 획 성격: 후보 끝면 `square`, 꺾임 `round`. 둥근 붓촉과 자모 경로·곡률 유지
- 1차 작업 대상: 공간 구조와 조합 배치
- 2차 작업 대상: 사용자 검수에 따른 공간 보정
- 3차 작업 대상: 필요한 경우에만 자모 형태 보정

### 지금 이용제 분류를 쓰는 범위

지금 쓴다. 그러나 역할은 검수뿐이다.

- 사용: 같은 구조군에서 후보가 일관되는지 확인
- 사용: 19개 초성과 종성 유무를 대표 표본으로 줄여 확인
- 미사용: 분류군 평균을 곧바로 레이아웃 값으로 변환
- 미사용: 한 글자의 결과를 같은 군 전체에 자동 복사
- 향후 규칙화 조건: 같은 군에서 같은 방향의 사용자 보정이 반복되고, 실제 조합 검증도 통과할 때

근거: [`src-next/ReferenceGroupLabPage.tsx`](../../src-next/ReferenceGroupLabPage.tsx)는 현재 분류가 비교용 단순화이며 실제 조합별 검증이 별도로 필요하다고 명시한다.

### 레거시 운영 방식

`레거시를 갱신해 계속 반영`하지 않는다.

1. 현재 레거시를 `legacy-noto-initial-v1`로 동결한다.
2. ㄱ 한 행만 사용한 `preset-v0-r1`은 폐기 이력으로 동결한다.
3. 자동 추출기가 새 값을 내면 `extractor-candidate-vN`을 만든다.
4. 기존 값과 새 값의 문자별·역할별 차이를 보여준다.
5. r1·r2·r3을 폐기하고, r4부터 초성 v3·홀자 G0/v9·종성 v1을 글자 단위 입력으로 결속한다.
6. 기존 리비전은 재현 가능하게 보존한다.

이 방식이면 기준선 추출 트랙이 계속 바뀌어도 배포 후보가 흔들리지 않는다.

## 두 트랙

```text
트랙 A — 기준선 추출
정확 문맥별 관찰 → 신뢰도/근거 → 사용자 검수 → 승인된 분석 자료
                                             │
                                             │ 명시적 승격만
                                             ▼
트랙 B — 배포 프리셋
Noto v0 동결 → 앱 자모에 공간 구조 적용 → 화면 검수 → 보정 → OTF 검수 → 배포 승인
```

### 트랙 A: 기준선 추출

- 장기 정확도를 만드는 연구·분석 트랙
- 폰트 SHA, 축, 초성, 실제 중성, 실제 종성을 포함한 정확 문맥으로 저장
- 실패·모호성도 값으로 채우지 않고 `abstained`로 보존
- 새 결과는 배포 프리셋의 입력 후보일 뿐 제품값이 아님
- 이 트랙의 완료는 v0 출시 선행 조건이 아님

### 트랙 B: 프리셋 제작

- 배포 일정을 지키는 제품 트랙
- 현재 확보된 Noto 자료로 바로 시작
- 입력을 불변 스냅샷으로 고정한 뒤 후보를 생성
- 사용자 확인과 수정이 핵심 승인 절차
- 첫 프리셋 승인 뒤 다중 프리셋 UI와 다중 폰트 집계를 별도 진행

### 두 트랙의 접점

- 자동 동기화 없음
- 새 추출 배치마다 `현재 프리셋 대비 차이표`만 생성
- 차이가 작아도 사용자 승인 전 미반영
- 같은 글자·같은 구조 역할만 직접 비교
- 넓은 문맥 레거시 값을 다른 중성·종성에 정확값처럼 재사용하지 않음

## 대표 입력 세트

홀자 목표는 다음 42자를 중심으로 만든다.

```text
초성 ㄱ × 현대 중성 21개 × {종성 없음, 종성 ㄱ} = 42자
```

닿자 목표는 별도로 다음 전체 레거시 범위를 사용한다.

```text
Noto 레거시 19초성 × 6문맥 = 114글자 · 상하선 관찰 342개
```

이유:

- 초성을 ㄱ 하나로 고정해 중성과 종성 유무에 따른 공간 변화만 본다.
- 현대 중성 21개를 모두 포함해 세로·가로·혼합 구조를 빠짐없이 건드린다.
- 종성 없음/있음을 모두 포함해 6개 조합 레이아웃을 전부 다룬다.
- 현재 골드 14자와 P1 범위 28자가 정확히 합쳐진다.
- 홀자 역할은 ㄱ으로 고정해 비교하되, 닿자 배치는 19초성을 빠짐없이 반영한다.

42자 홀자 보드와 19초성·6문맥 닿자 보드를 함께 확인한 뒤, 이용제 구조군 대표 종성으로 일반화 실패를 검사한다.

중요한 범위 구분:

- `noto-sans-kr.v1.json`의 키는 19초성이고, 받침 있는 세 문맥의 실제 종성은 모두 `ㄱ`으로 고정돼 있다.
- r3가 사용했던 레거시 받침 관찰 114개는 폐기 이력이다. 새 경로는 종성 v1의 27종 × 대표 3문맥 81건을 쓰며 사용자 시각 승인 전에는 후보 계산을 잠근다.
- [`src-next/ReferenceGroupLabPage.tsx`](../../src-next/ReferenceGroupLabPage.tsx)의 현대 종성 27종 윤곽·구조군 자료는 분류·검수 자료다. 종성별 수치 기준선 스냅샷은 아니다.
- 27종 전체에 `ㄱ`의 상·하선을 복사하지 않는다. Noto 종성 추출 배치를 따로 만든 뒤 다음 후보 리비전에서 사용한다.

## 데이터 우선순위와 결측 정책

동일 글자·동일 역할에서만 아래 우선순위를 적용한다.

1. `approved-analysis-gold`
2. 사용자가 이번 작업에서 승인한 자동 추출 후보
3. 동결한 Noto 레거시 값
4. 현재 앱 기본 레이아웃

규칙:

- 값 없음, 역할 불명, 추출 포기는 `0`이나 평균으로 채우지 않는다.
- 결측 필드는 현재 앱 값을 유지하고 `current-fallback`으로 표시한다.
- P1 v9 자동 후보 28자는 좌표·reference mode·anchor·가시 구간이 사용자가 확인한 v8 값과 같은 observation digest이므로 그 관찰 승인 범위만 승계한다. 출처 등급은 계속 `automatic-candidate`이며 골드나 제품값은 아니다.
- 무효화된 P1 v4·v6·v7·v8 값은 프리셋 입력으로 쓰지 않는다.
- 모든 필드에 `source`, `sourceVersion`, `status`, `fontSha256`, `contextKey`를 남긴다.
- Noto 파일은 SHA-256 `194018e6b2b293a7964f037b25c0249ce1418bc9ab3c971060a03aa57861e252`, `wght=400`, UPM 1000, baselineY 880으로 고정한다.
- 다른 SHA나 축으로 재생성되면 같은 자료가 아니라 새 버전으로 취급한다.

## 외부 기준선에서 앱 레이아웃으로 옮기는 법

외부 폰트 좌표를 `LayoutSchema` 숫자에 직접 복사하지 않는다.

외부 추출값은 획의 보이는 면 좌표다. 앱 레이아웃 값은 자모가 놓이는 박스와 분할선이다. 의미가 다르다.

변환 절차:

1. 앱 자모 경로는 기준선 수치를 화면에 투영할 렌더링 운반체로 고정한다. 앱 기본 위치값은 목표가 아니다.
2. 현재 공통 잉크 리졸버로 홀자 42자와 닿자 19초성×6문맥의 실제 출력 면을 측정한다.
3. 같은 글자·같은 역할의 Noto 목표 면과 차이를 계산한다.
4. `Split + Padding` 제약 안에서 6개 조합 레이아웃의 공통 분할·간격을 조절하고, Noto 레거시의 초성별 차이는 `choseongIs` 조건 override로 보존한다.
5. 앱 자모의 실제 출력 면이 목표에 가까워지는 후보를 찾는다.
6. 값은 0.005 단위, 즉 1000 UPM 기준 5유닛으로 스냅한다.
7. 숫자 오차 최소화만으로 확정하지 않고 화면에서 공간 균형을 확인한다.

곡선 관찰값 적용 원칙:

- `axis-aligned-face` 선은 기록된 유한 구간 안에서만 면 위치 목표로 쓴다.
- `start-side-local-tangent` 점은 곡선 시작 위치와 그곳의 국소 방향만 제약한다. 점의 y값을 가로보 전체 높이로 늘이지 않는다.
- G2는 현재 앱 자모 경로를 이동·스케일할 뿐 경로 형태를 바꾸지 않는다. 현재 곡선은 그대로 곡선이고 현재 직선은 그대로 직선이다.
- 외부 곡률을 한 점에서 자동 추정하거나 Noto 윤곽을 복사하지 않는다. 곡률 변경은 G5에서 시작·끝·접선 또는 제어점 근거를 갖춘 별도 형태 보정으로 다룬다.

레이아웃 저장 원칙:

- `splits`, `gaps`, `partOverrides`, 필요 시 `partOverridesByJungseong`에 후보를 저장
- `userPartOverrides`는 사용자 2차 보정용으로 비워 둠
- `BoxConfig` 직접 저장 금지
- 네 개 단독 자모 레이아웃은 이번 공간 후보에서 변경하지 않음
- 여섯 개 조합 레이아웃만 후보화

관련 계약:

- [`src/types/index.ts`](../../src/types/index.ts): 0–1 좌표와 Split/Padding 스키마
- [`src/utils/layoutCalculator.ts`](../../src/utils/layoutCalculator.ts): 스키마에서 박스 계산
- [`src/services/glyphInkResolver.ts`](../../src/services/glyphInkResolver.ts): 화면·OTF 공용 잉크 계산

## 실행 단계

### G0. 범위와 입력 동결

상태: **완료**

작업:

1. Noto 파일 SHA, wght 400, UPM 1000, baselineY 880을 확인한다.
2. 현재 레거시 JSON을 수정 없이 참조하는 불변 매니페스트를 만든다.
3. 깨끗한 신규 프로젝트의 자모·레이아웃·전역 스타일 digest를 만든다.
4. 사용자 localStorage 값은 입력에서 제외한다.
5. 이번 후보의 변경 가능 영역을 여섯 조합 레이아웃으로 제한한다.

통과 조건:

- 같은 입력을 다시 읽어도 digest가 같다.
- 출처가 없는 필드가 없다. 결측도 명시적 상태를 가진다.
- 후보 상태가 `productionEligible: false`다.

### G1. 42자 Noto 관찰 세트 완성

상태: **완료 · v4·v6·v7·v8 폐기 · v9 동일 관찰 승인 승계**

작업:

1. 골드 14자를 매니페스트에 넣는다.
2. P1 재현 명령으로 Noto 28자를 다시 추출한다.
3. 보고서에 기록된 원본 전체 SHA와 재생성 결과를 비교한다.
4. 각 역할의 값·근거·신뢰도·포기 사유를 기록한다.
5. P1 28자를 읽기 전용 보드로 사용자에게 먼저 보여준다.

통과 조건:

- 42자 모두 문맥 키를 가진다.
- 모든 기대 역할은 값 또는 명시적 abstention을 가진다.
- NaN, Infinity, 누락된 출처 없음.
- 사용자 미검수 P1 값은 승인 상태로 위장되지 않는다.
- 사용자 확인을 거친 자동 후보도 `approved-analysis` 골드나 제품값으로 위장되지 않는다.

### G2. 공동 조합 입력 r4

상태: **입력 연결 완료 · r1/r2/r3 폐기 · 무받침 fitter 대기**

작업:

1. 초성 v3 114건, 홀자 42건, 종성 v1 81건을 같은 Noto identity와 좌표계로 검증한다.
2. 각 글자 입력을 CH/JU/JO로 함께 묶는다.
3. 대표 ㅏ·ㅗ·ㅘ에서 다른 홀자로 옮기는 값은 `structure-context-projection`으로 표시한다.
4. 무받침은 fitter 입력을 열고, 받침은 종성 사용자 시각 승인 전 차단한다.
5. 후보 스타일을 `linecap=square`, `linejoin=round`, 둥근 붓촉으로 한 계약에 고정한다.
6. 다음 fitter는 외곽면끼리 비교하고 CH/JU/JO 실제 잉크 충돌을 hard gate로 둔다.

통과 조건:

- 네 단독 레이아웃과 자모 데이터는 입력과 byte-equivalent다.
- 여섯 조합 레이아웃만 바뀐다.
- 모든 박스가 유한수이며 너비·높이가 양수다.
- 같은 입력으로 반복 실행 시 같은 JSON이 나온다.
- `userPartOverrides`는 비어 있다.
- 목표 오차가 현재보다 악화된 문자는 별도 예외 목록에 남는다.
- 레거시가 새 생성 입력에 포함되지 않는다.
- 받침 포함 조합은 종성 검증 전 생성되지 않는다.

### G3. 1차 화면 검수

현재 확인 상태:

- 19초성 기준선 입력: **초성 v3 114/114 연결 · 사용자 승인 완료**
- 현대 종성 27종 입력: **v1 81/81 후보 · 구조 pass · 사용자 시각 검수 pending**
- 42자 단일 보드: **19초성 전환 · 무받침/ㄱ 상태 분리 · 카드별 Noto/현재 앱/r4 대기 캔버스 · E2E 확인 완료**
- 실제 r4 글자 후보: **미생성 · 공동 fitter와 충돌 gate 구현 대기**

진행 조건:

- r2의 19초성 확인은 ㅏ 대표 문맥 한 화면과 잘못 연결된 문맥축에 근거했으므로 승인으로 보존하지 않는다.
- Noto 27종 종성 수치 추출·사용자 검수가 끝날 때까지 프리셋 확정과 사용자 공간 보정은 대기한다.
- 추출 완료 후 기존 r2를 덮어쓰지 않고 종성 입력을 포함한 새 리비전을 만든다.

검수 순서:

1. 42자 앵커 보드
2. 이용제 구조군 대표 초성 보드
3. 종성 구조군 대표 보드
4. 기존 10개 문장
5. 큰 크기와 작은 크기

한 번에 보는 항목:

- 초성/중성 간격
- 초성/종성 높이 관계
- 세로·가로·혼합 조합 간 무게중심
- 받침 유무에 따른 상하 압축
- 외곽 여백과 글자폭
- 구조군 안의 반복되는 어긋남

통과 조건:

- 사용자가 `레이아웃 보정 시작 가능` 또는 수정 목록을 명시한다.
- 구조군 하나의 문제를 전체 규칙으로 곧바로 일반화하지 않는다.
- 각 수정 요청은 문자, 문제, 방향, 강도로 기록된다.

### G4. 사용자 2차 보정

작업 원칙:

1. 먼저 레이아웃만 수정한다.
2. 한 리비전에서 한 종류의 원인만 바꾼다.
3. 변경 후 42자 → 구조군 → 문장 순서로 재검수한다.
4. 반복되는 구조군 수정은 규칙 후보로 기록하되 아직 생성 규칙으로 승격하지 않는다.
5. 레이아웃 승인 후에만 자모 형태 수정 라운드를 연다.

리비전:

- `r1`: Noto 닿자 레거시를 ㄱ 한 행으로 축소해 폐기
- `r2`: Noto 레거시 문맥축 교차 연결로 폐기
- `r3`: 공동 조합 실패와 측정 의미 불일치로 폐기
- `r4-input`: 초성 v3 + 홀자 G0/v9 + 종성 v1 공동 입력. 받침은 검수 잠금
- `r4-candidate+`: 공동 fitter·충돌 gate 통과 뒤 생성할 실제 공간 후보
- 각 리비전은 이전 버전과 차이, 이유, 승인자를 보존

통과 조건:

- 사용자가 공간 구조를 승인한다.
- 형태 수정이 필요하면 별도 변경 목록이 있다.
- 승인 전 후보가 앱 기본 프리셋으로 로드되지 않는다.

### G5. 자모 형태 보정

공간 승인 후 필요한 경우만 수행한다.

범위:

- 획 끝, 굵기, 굴림, 특정 자모 비례
- Noto 윤곽 복사 금지
- 앱의 기존 자모 형태를 출발점으로 한 독자 보정

통과 조건:

- 공간 문제와 형태 문제를 분리해 기록한다.
- 바뀐 자모가 모든 조합 문맥에서 회귀 검사를 통과한다.
- Regular 400의 획 밀도가 문장 단위에서 균일하다.

### G6. OTF·배포 후보 검증

작업:

1. 승인 후보로 화면과 OTF를 같은 FontData에서 생성한다.
2. 현대 한글 11,172자와 호환 자모 51자를 생성한다.
3. 생성 실패, 빈 글리프, 잘못된 contour, NaN을 검사한다.
4. macOS 설치·재실행·문장 렌더링을 확인한다.
5. 화면 캡처와 설치 OTF 캡처를 비교한다.
6. 사용자 최종 승인 후에만 제품 프리셋 등록 플랜을 연다.

통과 조건:

- 화면과 OTF가 같은 레이아웃·잉크 리졸버를 사용한다.
- 총 11,223개 대상 글리프 생성 경로가 실패 없이 끝난다.
- 저장/재실행 후 결과가 변하지 않는다.
- 후보 JSON의 `productionEligible` 변경은 별도 명시적 승인 커밋에서만 일어난다.
