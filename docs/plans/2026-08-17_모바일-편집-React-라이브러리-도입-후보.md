# 모바일 편집 React 라이브러리 도입 후보

관련 문서: [2026-08-17_모바일-트랙패드-편집](./2026-08-17_모바일-트랙패드-편집.md), [2026-08-17_모바일-자소-캐러셀-편집](./2026-08-17_모바일-자소-캐러셀-편집.md), `옵시디언 2026-08-17_자동-저장과-편집-히스토리`

모바일 편집기를 구현할 때 기존 코드를 전면 교체하지 않는다. 범용적인 렌더링 최적화와 입력 동작만 검증된 React 라이브러리에 맡기고, 자소 후보 생성·스냅·좌표 변환·저장 범위 같은 폰트 편집 규칙은 프로젝트 코드로 유지한다.

## 우선 검토 순서

1. `@tanstack/react-virtual`: 전체 글자 목록에서 화면에 보이는 셀만 렌더링하도록 개선한다. 모바일 성능 개선 효과가 가장 클 것으로 본다.
2. `@use-gesture/react`: 새 모바일 트랙패드의 드래그 시작·이동·종료, 축 제한, 터치 취소 같은 입력 수명주기를 맡긴다. 기존 획 편집기를 먼저 전면 교체하지는 않는다.
3. `embla-carousel-react`: 상단 자소 캐러셀의 스와이프·스냅·활성 인덱스를 맡긴다. 활성 파트에 따른 글자 후보 생성은 기존 기획 규칙을 따른다.
4. `zundo` 또는 Immer Patch: 전체 상태 복제 비용을 줄일 수 있는지 작은 실험으로 검증한다. 타임스탬프, 행동 단위 묶기, 비파괴 복원 등 제품 히스토리 규칙을 대체하지 않는다.

## 보류·제외

- `Vaul`: 유지보수 중단 상태라 새 핵심 의존성으로 도입하지 않는다. 하단 드로어는 현재 Radix 기반 Sheet를 유지하고 필요한 동작만 보완한다.
- React Router 교체: 모바일 편집 개발의 즉각적인 이점이 작고 뒤로 가기·선택 복원 규칙에 영향을 줄 수 있어 후순위로 둔다.
- Canvas/Konva/Fabric 계열로 SVG 편집기 전면 교체: 미리보기와 폰트 출력의 형태 일치, 좌표·스냅 규칙이 흔들릴 위험이 커서 현재 범위에서 제외한다.
- Zustand·Immer·Radix 전면 교체: 현재 구조에 적합하므로 유지한다.

## 판단 상태

- 사실: 현재 글자 목록, 터치 제스처, 히스토리에는 직접 구현한 범용 동작이 많다.
- 가설: 가상화가 가장 큰 성능 개선을 만들고, 제스처·캐러셀 라이브러리가 모바일 구현 비용을 줄일 수 있다.
- 미결정: 각 라이브러리의 실제 도입 여부는 모바일 편집기 구현 단계에서 작은 실험과 성능 측정 후 확정한다.

위 순서는 라이브러리 교체의 성능 효과를 비교한 순서다. 모바일 v2 제품 개발은 별도의 세로 흐름으로 진행한다.

`획 선택 → 트랙패드 제스처 → 행동 단위 저장·복원 → 자소 캐러셀 → 글자 배치 → 획 스타일`

따라서 글자 목록 가상화는 별도 성능 개선으로 진행하되, 모바일 v2 첫 개발 단위를 막는 선행 조건으로 두지 않는다. `@use-gesture/react`와 행동 기록 방식의 작은 실험을 첫 세로 흐름에 포함한다.
