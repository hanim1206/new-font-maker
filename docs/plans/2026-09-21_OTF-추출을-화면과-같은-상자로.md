# OTF 추출을 화면과 같은 상자로

- **이번에 비교하는 것**: OTF 추출기가 자소 상자를 옛 split/padding 스키마에서 가져오는 지금과, 화면과 같은 칸 해석(Noto 모델 상자 + 저장된 레이아웃 Δ)에서 가져오는 것.
- **이번 승인으로 바뀌는 것**: 내려받은 OTF의 글자 비례가 앱 화면과 같아진다. 레이아웃 탭에서 고친 Δ가 OTF에 들어간다. 옛 OTF 기준 스냅샷(e2e)은 새 기준으로 옆에 하나 더 둔다.
- **바뀌지 않는 것**: 획·두께·획 끝을 윤곽으로 바꾸는 길(`strokeToContours`·붓촉·합치기), 글자 폭(advance)·Design Body·자간 규칙, 폰트 이름·cmap, 화면 렌더, 모델과 Δ 저장, production 값.

출처: 9/21 주간 노트 "OTF 추출한 서체가 앱에서 보던 것과 다르다". 원칙: 실제 글자를 먼저 보여 준다 — 화면에서 본 글자와 받은 글자가 다르면 편집이 의미가 없다.

## 지금 상태

**사실** (코드 읽기)
- 화면(`AppGlyph` · 자소 탭 · 검수 격자 · 문장 보정)은 `useContextPlacement` → `resolveContextBoxes({ identity, model, syllable, ends, delta })`로 상자를 구한다. 모델이 글자를 완전히 풀면(`complete`) 모델 상자, 아니면 스키마로 돌아간다.
- 추출기(`src/services/fontExportUtils.ts:145`)는 늘 `placement: { kind: 'schema' }`다. 모델도 Δ(`layoutDeltaStore`)도 안 읽는다. 9/17에 Noto 프리셋이 옛 프리셋을 대체할 때 추출기만 안 옮겨졌다.
- 상자를 받은 뒤의 길은 화면과 추출기가 같다. 둘 다 `resolveGlyphInkPrimitives`를 거치고 같은 전역 스타일(굵기·획 끝·붓촉)을 읽는다.
- `resolveContextBoxes`는 `src/services`의 순수 함수다. 모델 묶음(`notoPresetGlyphs.model()`, 비동기)과 Δ 스토어만 `src-next`에 있다. `src`는 `src-next`를 import하지 않는다.
- 기본 획으로는 11,172자 전부 `complete`다(9/20 스윕). 독립 자모 51자는 모델 대상이 아니라 스키마로 그린다.
- 옛 OTF 고정 테스트: `tests/e2e/otf-legacy-baseline.spec.ts`(대표 12자 윤곽 스냅샷), `nonround-otf-baseline.spec.ts`, `src-next/font-export-contract.test.ts`.

**가설**
- 스크린샷의 굵기·둥근 획 끝 차이는 상자 차이로 설명되지 않는다. 코드상 같은 스타일을 읽으므로 폰트를 띄운 프로그램의 가짜 굵게이거나 저장된 스타일 값 차이일 수 있다. G0에서 잰다.

## 하려는 것

판단 변수 하나: **추출기 상자의 출처**.

1. `collectGlyphDataForChar`·`collectAllGlyphData`·`generateAndDownloadFont`가 선택 인자 `placementOf(syllable, schema)`를 받는다. 없으면 지금처럼 스키마. `src`가 `src-next`를 모르는 방향을 지킨다.
2. `fontExportStore.confirm`이 추출 전에 모델 묶음을 기다리고, 화면과 같은 규칙의 `placementOf`를 만들어 넘긴다: `identityOfSyllable` → `effectiveLayoutDelta(스토어 스냅샷, identity)` → `resolveContextBoxes` → `complete`면 boxes, 아니면 schema. 이 규칙을 `useContextPlacement`와 한 함수로 묶어 화면과 추출이 갈라질 수 없게 한다.
3. 글자 폭과 원점은 그대로 Design Body(실효 패딩)에서 낸다. 모델 상자도 화면에서 같은 em 좌표로 그려지므로 `x - padding.left` 투영을 그대로 쓴다.
4. 모델을 못 읽으면 추출을 멈추고 이유를 띄운다. 조용히 스키마로 떨어지면 오늘과 같은 "왜 다르지"가 된다.
5. 스키마로 떨어진 글자 수를 추출 결과에 남긴다(기본 획이면 0).

## 미결정

1. 옛 스냅샷 테스트 — `placementOf` 없이 부르는 길로 남긴다(추천, 레거시 동결 원칙) vs 새 기준으로 갈아 끼운다.
2. 모델 읽기 실패 — 추출을 멈춘다(추천) vs 경고 뒤 스키마로 추출한다.

## 이 플랜에 없는 것

- 굵기·획 끝 차이가 G0에서 진짜로 확인되면 그 수정은 따로 승인받는다(변수가 다르다).
- 자모 `layoutIs` 오버라이드를 화면이 읽게 하는 일(추출기만 읽고, 지금은 67자 전부 비어 있다).
- 부품 하나가 안 맞을 때 그 부품만 예외로 두는 일(`레이아웃-편집기-홀자를-앱-획으로` 단계 2).

사실
- 추출기: `collectGlyphDataWithPlacement(char, placementOf?)`를 더했다. `collectGlyphDataForChar(char)`는 인자 하나 그대로(기존 계약 테스트 유지). `generateAndDownloadFont`가 `placementOf`를 받고, 결과에 `schemaFallbackCount`를 남긴다. `src`는 여전히 `src-next`를 모른다.
- 화면·추출 공용 규칙 `contextPlacementOf`(`src-next/notoModel.ts`). `useContextPlacement`가 이 함수를 부르고, `fontExportStore`의 `placementResolverOf(모델, Δ 스냅샷)`도 같은 함수를 부른다. Δ는 추출 시작 때 한 번 뜬다.
- 모델을 못 읽으면 추출을 멈추고 이유를 `error`에 남긴다. 다음에 이름 창을 열면 그 이유가 보인다.
- G0 (`src-next/otf-screen-parity.test.ts`): `별을노래하는` 여섯 자 모두 OTF 상자 = 화면 상자(원점 이동만 빼고 완전히 같은 수). 옛 스키마 OTF는 화면과 xor 85~145% — 거의 다른 글자였다.
- G0 xor 기준은 고쳤다. 상자가 같아도 xor이 0.7~1.1% 남는데, OTF 좌표를 정수 폰트 단위로 반올림해서 생기는 가장자리 실선이다(같은 상자끼리도 0.06~0.75%). 그래서 "상자 완전 일치 + 가장자리 어긋남 평균 1유닛(1/1000em) 아래"로 쟀고 0.29~0.37유닛이다. 처음 적은 0.5%는 근거 없는 숫자였다.
- 굵기·획 끝 가설: **코드에서는 재현되지 않는다.** OTF의 ㅡ 획 폭 0.0700em = 화면 stroke-width 0.0700em, 획 끝 butt, 끝점 밖으로 0.0004em. 스크린샷의 굵고 둥근 모양은 기본 스타일 추출에서는 안 나온다.
- G1: 대표 12자(가 고 과 각 곡 곽 의 왜 뷁 힣 쌍 흙) 상자 일치. Δ 세 층(전체 · 이 레이아웃 · 이 자모)을 저장하면 OTF 상자가 움직이고 화면 상자와 계속 같다. 독립 자모(ㄱ ㅎ ㅙ)는 옛 스키마 출력과 같다.
- G2: 11,223 글리프, 음절 스키마 폴백 0, 컨투어 합치기 실패 0. `npm test` 938 통과 · 2 실패 — 둘(`preset-candidate-source` · `vertical-vowel-gap-reference` digest)은 이 변경을 빼고 돌려도 똑같이 실패한다.
- **G2 시간 기준 미달.** 브라우저 추출 전체 8.3초 → 19.8초(2.4배, 기준 1.5배). 늘어난 건 글자마다 획을 칸에 맞추는 `fitPartStrokes`(전수 약 10초)이고, 입력이 글자마다 거의 다 달라(36,841개 중 34,485개가 서로 다른 상자) 캐시로는 안 줄어든다. 수집을 100자씩 나눠 돌려 진행 표시는 안 멈춘다.
- 옛 스냅샷: `?otf=schema`면 옛 상자로 추출하는 문을 두고 `otf-legacy-baseline` · `nonround-otf-baseline`이 그 길로 돈다. 새 기준은 `tests/fixtures/model-otf-glyphs-v1.json` + `tests/e2e/model-otf-baseline.spec.ts`(통과).
- 옛 스냅샷 e2e 둘은 **이 변경 전부터 깨져 있었다.** 기본 획 끝을 butt/miter로 바꾼 커밋(501f2ee) 뒤로 기준 파일이 안 갱신됐다. `?otf=schema` 길의 차이(legacy -3647/+769, nonround -9/+9)가 변경을 빼고 돌린 것과 똑같아서, 스키마 길이 옛 출력을 그대로 낸다는 것만 확인했다. 기준 파일은 안 건드렸다.

가설
- 스크린샷의 굵고 둥근 글자는 (a) 기본 획 끝이 둥글던 때 저장된 스타일이 브라우저에 남아 있었거나 (b) 폰트를 띄운 프로그램이 굵게 그린 것. 다만 (a)라면 화면도 둥글어야 해서 설명이 다 되지는 않는다. G3에서 새로 받은 폰트로 다시 본다.

2. 깨져 있던 옛 스냅샷 둘 — 기준을 다시 뜬다 vs 옛 문장 보정 화면 제거 때 같이 지운다.
