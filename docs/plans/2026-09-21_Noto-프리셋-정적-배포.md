# Noto 프리셋 정적 배포

- **이번에 비교하는 것**: Noto 프리셋을 dev 서버 API로만 줄지, 빌드 결과물에 정적 파일로 실을지.
- **이번 승인으로 바뀌는 것**: `public/noto-preset/`에 모델·xor·글자 윤곽 파일이 생기고 git에 들어간다. 배포 빌드는 API 대신 이 파일을 읽는다. 배포된 앱의 글자 배치가 스키마에서 모델 상자로 바뀐다.
- **바뀌지 않는 것**: 모델 값과 윤곽 값 자체, 로더 인터페이스(`NotoPresetGlyphLoader`), dev 서버의 API 경로, OTF 내보내기(아직 스키마 배치), `Noto 배치` 토글과 스키마 fallback.

[2026-09-21_뼈대-탭-제거](./2026-09-21_뼈대-탭-제거.md)의 `다음 순서` 2번. 배포된 main에서 `Noto 프리셋을 읽지 못했습니다`가 뜨는 원인을 없앤다.

## 지금 상태

**사실** (코드 읽기 + 측정)
- `/api/noto-preset`은 Vite 플러그인이다(`scripts/reference-lab/notoPresetApi.ts:182`). `vite dev`와 `vite preview`에만 붙고 `dist/`에는 없다.
- 원본은 `.reference-fonts/guide-corpus/<runId>/analysis/`에 있고 `.gitignore`로 빠져 있다. 이 맥에만 있다. 호스팅 쪽에서 빌드하면 만들 재료가 없다.
- 제품 화면이 셋 다 쓴다. 모델 = `notoModel.ts`(문장 보정, 레이아웃 편집), 글자 윤곽 = `useNotoGlyph` · `notoGhostCompare`(고스트), xor = `ReviewWorkspacePage`(검수 격자 색).
- API 응답 크기: 모델 0.99MB(gzip 0.13MB), xor 0.38MB(gzip 0.09MB), manifest 1KB 미만, 글자 하나 약 5.5KB × 11,172자 = 61MB.
- 모델을 못 읽으면 `useContextPlacement`가 스키마 배치로 돌아간다. 그래서 지금 배포본은 화면과 OTF가 둘 다 스키마로 **일치**한다.
- PWA precache 패턴은 `js,css,html,ico,png,svg,woff,woff2`. json은 안 들어간다.

**가설**
- 글자 윤곽을 글자마다 한 파일로 두면 파일 11,172개라 git과 배포가 무겁다. 초성×중성 399묶음(묶음당 28자, 약 155KB, gzip 30KB 안팎)이 맞는 크기로 보인다. G1에서 잰다.

## 하려는 것

1. 내보내기 스크립트 `scripts/reference-lab/exportNotoPresetStatic.ts`. API와 같은 `createNotoPresetReader`를 그대로 써서 응답과 같은 바이트를 쓴다. 명령은 `npm run reference:noto-static`. **`npm run build`에 넣지 않는다.** 분석값이 배포 프리셋이 되는 건 사람이 명령을 돌리고 커밋할 때뿐이다(원칙: 자동 승격 금지).
2. 산출물 `public/noto-preset/`: `manifest.json` · `model.json` · `xor.json` · `glyphs/<초성중성 번호>.json` 399개 · `OFL.txt`.
3. 로더(`notoPresetGlyphs.ts`)의 `fetchJson` 아래에 주소 해석만 끼운다. 배포 빌드는 정적 파일, dev는 지금처럼 API(새로 뽑은 값이 바로 보여야 하므로). `glyph(codepoint)`는 묶음을 받아 그 안에서 한 글자를 꺼내고, IndexedDB에는 지금처럼 글자 단위로 둔다. 캐시 키(stageKey)는 그대로.
4. dev에서도 정적 경로를 강제로 타는 스위치 하나(`?preset=static`). 배포 전에 로컬에서 같은 경로를 확인하는 용도.
5. 에러 문구를 나눈다. 파일이 없을 때 `Noto 프리셋 파일이 배포에 없습니다`처럼 원인을 말한다.

## 위험

- **화면과 파일이 갈라진다.** 모델이 배포되면 화면은 모델 상자, 내보낸 OTF는 스키마 배치(`fontExportUtils.ts:145`)다. 지금 배포본엔 없던 불일치가 새로 생긴다. 뼈대 탭 플랜은 그래서 OTF 전환을 먼저로 적었다. 미결정 1.
- git에 61MB(압축 전)가 들어간다. 윤곽을 다시 뽑을 때마다 통째로 바뀐다. 미결정 2.
- Noto Sans KR 윤곽을 파일로 다시 배포하게 된다. OFL 1.1은 라이선스 문서를 같이 두면 허용한다. `OFL.txt`를 함께 싣는다.

## 미결정 → 2026-09-21 답변

1. **순서** — 정적 배포 먼저(추천: 에러가 지금 사용자에게 보이고, OTF 전환은 어차피 모델이 배포돼 있어야 검증된다) vs OTF 전환 먼저. 먼저 하면 그 사이 배포본은 화면 ≠ OTF다. 출력 탭에 한 줄 안내를 둘지도 같이.
2. **글자 윤곽의 자리** — git에 같이 넣음(추천: 호스팅이 뭐든 동작) vs 모델·xor만 git에 넣고 윤곽은 배포 때 따로 올림. 뒤쪽은 배포 방법을 알아야 설계할 수 있다.
3. **배포 방법** — main이 어디에 어떻게 올라가는지 레포에 설정이 없어 모른다(`vercel.json` · `netlify.toml` · workflow 없음). G3 주소와 2번 판단에 필요.
