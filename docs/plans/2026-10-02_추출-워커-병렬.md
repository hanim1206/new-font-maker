# 추출 워커 병렬

- **이번에 비교하는 것**: 지금 추출(메인 스레드 직렬) 대 Worker 여러 개가 글자 범위를 나눠 수집·윤곽 변환을 하는 추출. 같은 폰트 데이터에서 바이트 동일성과 걸린 시간을 잰다.
- **이번 승인으로 바뀌는 것**: 추출의 수집·변환이 Worker 풀에서 돈다. Worker 수와 글자 분할 방식 한 가지. 실패하면 지금 경로로 폴백.
- **바뀌지 않는 것**: 만들어지는 OTF 바이트(같은 입력 → 같은 파일), 화면 미리보기·편집기, 저장 데이터, 단순화 ε1(앞 플랜), 진행 표시의 단계 구분.

## 왜

점 줄이기 플랜(10-02)으로 하니무스 손글씨체가 94 → 55초. 남은 직렬 구간은 수집 27초 + 윤곽 변환 19초이고 둘 다 글자 단위로 독립이다. 추출은 이미 브라우저 밖(vite-node)에서 스토어를 메모리로 채워 통째로 돈다 — 메인 스레드 없이도 되는 게 증명돼 있다.

## D0 계약 초안

- **한 변수**: Worker 수 = `min(hardwareConcurrency - 1, 상한)`과 글자 분할 방식(연속 범위 등분). 상한 후보 4 · 6 · 8.
- **방법**: Worker가 `collectFontData()` 스냅숏 + 노토 모델 + 레이아웃 Δ + 전역 스타일을 받아 `applyFontData()`로 자기 스토어를 채우고, 맡은 범위의 수집 + 변환 + CharString 굳히기까지 해서 바이트로 돌려준다. 메인은 글리프 순서대로 모아 조립 · 서브루틴 · 패키징만 한다.
- **지키는 것**: 같은 입력 → 같은 OTF 바이트(글리프 순서 · cmap 동일). Worker를 못 띄우면(또는 하나라도 죽으면) 지금 메인 스레드 경로로 폴백 — 서브루틴 Worker와 같은 규칙. 진행 표시는 Worker 보고를 합쳐 지금 단계 구분 그대로.
- **건드리지 않는 것**: 속공간 WIP 파일(`counterKeep.ts` · `glyphInkResolver.ts` 등)은 import만 한다.
- **미결정**: Worker 수 상한(G0에서 정한다), 모바일(아이폰) 메모리 — Worker마다 스토어 사본이 생긴다. G2에서 실제 기기로 확인.

## 게이트

| 게이트 | 무엇을 | 통과 기준 |
|---|---|---|
| D0 | 위 계약 승인 | 사용자 승인 |
| G0 대표 | 하니무스 + 기본 폰트 전수를 Worker 1 · 2 · 4 · (코어 되면 6)로 추출, 시간 표 | Worker 수에 따라 시간이 준다. 바이트가 직렬 결과와 동일 |
| G1 홀드아웃 | 분할 경계를 바꿔(등분 vs 다른 등분) 두 번 추출 | 바이트 동일 — 분할이 결과에 영향 없음 |
| G2 전수 | 브라우저(데스크톱 + 아이폰)에서 실제 추출 | 검사 오류 0 · 크래시 없음 · 아이폰 메모리 안 터짐 · 진행 표시 정상 |
| G3 사용자 | 사용자가 실제 기기에서 받아 설치 | 사용자 확인 |

시간 목표는 G0 결과를 보고 정한다(가늠: 4코어에서 55 → 20~25초).

## 진행 기록

**2026-10-02**
- 사실: 직렬 남은 구간 — 수집 27초(속공간 보정 13초 포함) · 변환 19초 · 조립+서브루틴 ≈8초 · 패키징 0.4초(하니무스, 점 줄이기 적용 후 55초).
- 사실: `collectFontData()` ↔ `applyFontData()` 짝이 있어 Worker 스토어 채우기 입구로 쓸 수 있다. 서브루틴 Worker(`cffSubroutinizeRunner.ts`)가 폴백 패턴의 선례.
- 가설: 수집·변환이 글자 단위 독립이라 N분할로 거의 선형으로 준다. Worker 띄우기 + 스토어 채우기 고정비는 Worker당 1초 안쪽일 것(G0에서 잰다).
- 미결정: Worker 수 상한, Node 스크립트(vite-node)에서 G0를 재는 방식 — `worker_threads`로 같은 코드가 돌아야 한다. 안 되면 G0만 브라우저에서 잰다.
- 결정: D0 승인(사용자, 10-02).

**2026-10-02 G0**
- 사실: 운반형 `PortableHangulGlyph` + `portableHangulGlyphOf()` + `generateFontBuffer`의 `hangulPortables` 옵션(주면 수집 · 변환 건너뜀, 기본 없음 = 지금 경로 그대로). 측정은 `scripts/font-check/parallelExportG0.ts` — 자식 vite-node 프로세스가 Worker 대역.
- 사실(하니무스 전수, 이 맥 · 같은 판에서 직렬 59.8초): 워커 1 = 64.4초(오버헤드 +4.6) · 2 = **43.5** · 4 = **35.9** · 6 = **33.9초**. 네 판 전부 직렬과 바이트 동일(head 날짜 · 체크섬만 빼고 비교). 조립(서브루틴 포함) 10초가 직렬 바닥.
- 사실: 자식 띄우기 + 운반 고정비 ≈ 6초(vite-node 부팅 + 스토어 채우기 + JSON). 브라우저 Worker는 이보다 가벼울 것.
- 사실: 연속 등분이라 부하가 안 고르다(워커 2에서 20.7 대 29.6초 — 뒷범위 받침 글자가 무겁다). 끼워넣기(stride) 분할 + 부모 재정렬이 후보.
- 가설: 브라우저에선 고정비가 작아 워커 4~6에서 25~30초. 조립 10초를 더 줄이려면 서브루틴을 운반형 도착 순서대로 겹치기(다음 후보).
- 미결정: Worker 수 상한(4 대 6 — 6은 4 대비 2초 이득), stride 분할 채택 여부.
- 결정: G0 닫힘 + G1 닫힘(분할 1 · 2 · 4 · 6 네 가지 경계 전부 직렬과 바이트 동일 = 경계 불변).

**2026-10-02 브라우저 구현**
- 사실: 제품 경로 구현 — `fontExportParallel.worker.ts`(스냅숏으로 스토어 채우고 범위 운반형 생산) + `fontExportParallel.ts`(풀 · stride 분할 · 실패 시 null 폴백, 상한 6 · 코어−1, 2개 미만이면 직렬) + `fontExportStore` 연결(수집 0.6 비중으로 진행 단계 유지).
