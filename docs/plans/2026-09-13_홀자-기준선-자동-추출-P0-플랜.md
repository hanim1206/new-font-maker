# 홀자 기준선 자동 추출 P0 플랜

## 목적

사용자가 폰트와 첫닿자·홀자·받침을 고르면 완성 글자를 즉석 조합하고, 실제 폰트 윤곽에서 홀자의 기둥·보 바깥 면 후보를 계산해 같은 캔버스에 보여 준다. 사람이 조합마다 값을 처음부터 입력하지 않고 후보를 검토·수정·거부하게 만드는 것이 목표다.

자동 결과는 외부 폰트 분석 후보다. `LayoutProfile`, `JamoMaster`, `ContextPreset`, OTF 기본값에는 자동 반영하지 않는다. 상위 측정 계약과 데이터 소유권은 [2026-09-13_홀자-기준선-측정값-수집-플랜](./2026-09-13_홀자-기준선-측정값-수집-플랜.md)을 따른다.

상태: G0~G4 완료. 사용자가 고정 나눔고딕 위험 표본 24카드를 확인했다. P0는 정확한 SHA의 등록 폰트 범위에서 닫고, 21홀자·전체 받침·임의 업로드는 별도 확장 단계로 넘긴다.

## 현재 기반

- `src-next/FontGuideLabPage.tsx`는 첫닿자·홀자·받침으로 완성 글자를 조합하고 outline과 유한 구조면 후보를 같은 카드에 표시한다.
- `scripts/reference-lab/server.py`는 FontTools outline과 `POST /api/reference/v1/medial-guide-candidates`를 제공하고 후보를 메모리 캐시한다.
- `scripts/reference-lab/medial_guide_extractor.py`는 면 위치와 외부 윤곽에서 실제 보이는 복수 구간을 독립적으로 계산하며 숨은 접합점과 비정형 곡면은 자동 포기한다. 사용자가 방향을 정한 사례만 시작쪽 국소 접선을 별도 provenance로 허용한다.
- `src-next/medialGuideCandidateModel.ts`는 `candidate | abstained` 응답과 요소별 `face | visibleSpans` 계약을 런타임에서 검증한다.
- `src-next/medialGuideCandidateCache.ts`는 후보·자동 포기를 폰트·축·글자·path·추출기·역할 버전 identity로 분리해 브라우저에 최대 600개 보관한다.
- 화면 주소는 `/font-guide-lab?font=...` 하나를 유지한다. `section=medial|final`과 `/medial-guide-lab`은 통합 화면으로 돌아가며 별도 작업 공간을 만들지 않는다.
- 기존 v2 scalar 관측은 이관 근거로만 남고 새 v3 후보를 gold나 생산값으로 자동 승격하지 않는다.
- 현재 서버의 variable font 축은 catalog 값으로 고정된다. P0에서 사용자가 축을 바꾸는 기능은 다루지 않는다.

## P0 범위

### 포함

- 서버 catalog의 정확한 파일 SHA에 고정된 Noto Sans KR과 나눔고딕만 허용한다. 임의 파일은 받지 않는다.
- 홀자 `ㅏ·ㅓ·ㅣ·ㅗ·ㅜ·ㅡ·ㅘ`를 다룬다.
- 현대 첫닿자 19자 전부를 조합할 수 있게 한다.
- 받침은 `없음`과 `ㄱ`만 다룬다.
- 역할은 긴 기둥 면, 보 면, 짧은 세로줄기 위치 면·진행 방향 끝면 중 각 홀자에 정의된 것만 계산한다. P0 안정 ID는 `outerPillarFace`, `primaryBeamFace`, `basePillarFace`, `baseStemTipFace`, `upperBeamFace`, `lowerBeamFace`다.
- 후보·자동 포기 결과 캐시, 캔버스 오버레이, 채택·수정·거부 흐름을 연결한다.

전체 조합 수는 `19 × 7 × 2 = 266`이다. 전부 미리 계산하지 않고 사용자가 연 조합만 계산한다. 자동 회귀 검사에서는 266개 전체를 batch로 확인한다.

### 제외

- 임의 `.otf/.ttf` 업로드
- 사용자가 variable font 축을 바꾸는 기능
- ㄱ 외 26개 받침
- 나머지 홀자 14자
- 생산용 레이아웃·자모 구조·폰트 출력값 자동 생성
- 머신러닝·LLM 판정

임의 폰트 업로드는 두 번째 등록 폰트 검증을 통과한 뒤 별도 단계로 연다.

## 핵심 결정

### 서버에서 추출한다

후보 계산은 브라우저에서 SVG path 문자열을 다시 해석하지 않고 Python 분석 서버에서 수행한다. FontTools의 분해된 segment를 그대로 쓸 수 있고 composite glyph와 곡선을 한 계약에서 처리할 수 있기 때문이다.

새 endpoint 후보:

```text
POST /api/reference/v1/medial-guide-candidates
```

요청은 `fontId`와 조합 사례 배열을 받는다. 각 사례는 `character`, `initialJamo`, `medialJamo`, `finalJamo`를 모두 가진다. 서버는 네 값의 한글 조합이 일치하지 않으면 요청 전체를 거부한다.

### 단일 정답 대신 후보 또는 자동 포기를 반환한다

```text
candidate
  value · score · confidence · alternatives · evidence

abstained
  reasonCode · evidence
```

`abstained`는 cache miss나 오류가 아니다. 분석기가 안전하게 역할 면을 고르지 못했다는 정상 결과다. 자동 포기도 캐시한다.

축에 평행하지 않은 곡면은 기본 `non-scalar-face`다. 사용자가 시작 방향을 명시한 검토 사례만 `referenceMode=start-side-local-tangent`로 반환한다. 이때 anchor, 시작 방향, 최대 편차, 짧은 가시 지지 구간을 함께 보내며 전체 구조면 후보로 확대하지 않는다.

reasonCode P0 범위:

- `glyph-missing`
- `unsupported-outline`
- `no-role-match`
- `ambiguous-role-match`
- `outside-analysis-roi`
- `non-scalar-face`
- `occluded-by-neighbor-overlap`

검토 상태는 후보 상태와 분리한다.

```text
pending | accepted | corrected | rejected
```

## 좌표·윤곽 계약

### 분해와 정규화

- composite glyph는 `DecomposingRecordingPen`으로 실제 contour까지 분해한다.
- 선·2차·3차 베지어를 구조화된 segment로 유지한다.
- 방향과 길이 판정용 평탄화 오차는 shared-baseline 좌표에서 최대 `0.5 unit`로 둔다.
- 추출 내부 계산은 float를 유지하고, 카드 표시와 raw 관측으로 옮길 때만 가장 가까운 정수로 반올림한다.

native font 좌표를 분석 캔버스 좌표로 바꾸는 식:

```text
scale = display.unitsPerEm / glyph.unitsPerEm
x = rawX × scale
y = display.baselineY - rawY × scale
```

현재 분석 캔버스의 `unitsPerEm=1000`, `baselineY=880` 계약을 그대로 사용한다. 원래 advance와 원점은 바꾸지 않는다.

### 분석용 ROI

홀자 탐색 영역은 production `LayoutProfile`이나 JamoMaster에서 가져오지 않는다. `right / bottom / mixed × 받침 유무`별 거친 비교 전용 ROI를 versioned fixture로 둔다. 이 영역은 홀자 경계나 JU PartFrame이 아니다.

- ROI는 기본으로 숨기고 G0 검토 토글을 켰을 때만 반투명 영역으로 표시한다.
- 포함 경계는 닫힌 경계로 처리하고, 섞임은 두 포함 영역 중 하나에 들어오면 수집한다.
- 첫닿·받침 고정 제외 사각형은 두지 않는다. ROI 안의 다른 자소 윤곽은 contour 역할을 분류해 제외하고, 분류할 수 없으면 `abstained`를 반환한다.
- ROI 밖 후보, 동점 후보, 역할 수보다 많은 유효 후보는 자동 선택하지 않는다.
- 초기 ROI는 G0에서 실제 글자 위에 표시해 승인받는다.

### 후보 생성

1. ROI와 겹치는 contour segment를 수집한다.
2. 거의 수직·수평인 이웃 segment를 같은 face 후보로 묶고, 짧은 세로줄기는 보와 접합하는 세로 contour의 방향 끝 extrema를 별도 후보로 만든다.
3. 역할별 방향, 위치 band, 길이, 연속성, 윤곽 바깥 면 방향, 보와의 접합 관계로 점수를 계산한다. `ㅗ·ㅜ`는 단일 줄기, `ㅛ·ㅠ`는 좌우 두 줄기를 독립 매칭한다.
4. 1위와 2위 후보 차이까지 포함해 신뢰도를 정한다.
5. 기준을 못 넘으면 값을 만들지 않고 `abstained`를 반환한다.

초기 점수 threshold는 gold tuning set으로만 조율한다. holdout을 보기 전에 threshold와 `extractorVersion`을 동결한다. 신뢰도 근거에는 최소한 ROI ID, contour/segment ID, face 길이, 방향 오차, 1·2위 점수 차이를 남긴다.

## gold와 holdout

현재 직접 입력한 Noto Sans KR 후보는 정답 자료가 아니다. 먼저 사용자가 실제 윤곽 위에서 수정·승인한 값만 gold fixture로 만든다.

### tuning set

첫닿 `ㄱ`과 P0 홀자 7자의 받침 없음/`ㄱ` 조합 14글자를 사용한다.

```text
가·각 / 거·걱 / 기·긱 / 고·곡 / 구·국 / 그·극 / 과·곽
```

추출 규칙과 threshold는 이 세트에서만 조율한다.

### holdout

`ㄱ·ㄷ·ㅁ·ㅍ·ㅎ × ㅏ·ㅗ·ㅘ × 받침 없음/ㄱ` 중 tuning set과 겹치는 `ㄱ` 사례를 제외한다. 열린 구조, 닫힌 구조, 돌출 구조, 복합 홀자를 함께 본다. 구현 중 holdout 정답을 보고 threshold를 다시 맞추지 않는다.

두 번째 등록 폰트는 별도 외부 holdout이다. Noto용 예외를 추가해서 통과시키지 않는다.

현재 직접 입력된 `ㅝ·ㅢ·ㅞ` 후보는 gold나 tuning 입력이 아니다. threshold와 `extractorVersion`을 동결한 뒤 구조가 다른 홀자에서 실패 양상을 보는 비공식 진단 자료로만 사용한다.

## 정확도 통과 기준

- 존재하지 않는 역할을 생성한 사례 `0건`.
- `high` 후보가 다른 구조 면을 선택한 사례 `0건`.
- gold와 같은 면을 선택했을 때 좌표 오차 `±2 shared-baseline unit` 이내.
- 단순 홀자 `ㅏ·ㅓ·ㅣ·ㅗ·ㅜ·ㅡ`의 holdout 후보 생성률 `80% 이상`.
- 혼합홀자 `ㅘ`의 holdout 후보 생성률 `50% 이상`.
- 모든 자동 포기에 reasonCode와 근거 존재.
- 전체 266개 batch에서 crash, NaN, 무한값, 정의되지 않은 역할 생성 `0건`.

후보 생성률을 맞추려고 신뢰도 기준을 낮추지 않는다. 정확도 기준을 지키지 못하면 범위를 줄이거나 P0를 보류한다.

## 캐시 계약

글리프 outline 캐시는 기존 서버 캐시를 유지한다. 후보 캐시는 raw 관측 저장소와 분리한다.

후보 키:

```text
fileSha256
+ normalized catalog axes
+ glyph codepoint
+ pathSha256
+ extractorVersion
+ roleDefinitionVersion
```

- 서버는 같은 실행 세션의 후보를 메모리에 캐시한다.
- 브라우저는 `reference-medial-guide-candidates-v1` 저장소에 candidate와 abstained를 함께 보관한다.
- P0 persistent cache는 최대 600개 entry만 유지하고 오래된 항목부터 제거한다.
- 파일 SHA, path SHA, 축, 추출기 버전, 역할 버전 중 하나라도 달라지면 재사용하지 않는다.
- 연속 선택 중 늦게 도착한 응답은 현재 요청 fingerprint와 다르면 버린다.
- raw 관측은 실제 `finalJamo: null | 'ㄱ'`를 키로 갖는 v3로 이관한다. `with-final` 하나에 여러 받침을 합치지 않는다.

P0에서 축은 catalog 고정값만 사용한다. 축 변경 UI와 API는 후속 범위다.

## 성공 후 활용 가설

자동 추출 성공은 기준선 입력 편의보다 문맥별 글자 구조를 비교 가능한 데이터로 바꾸는 데 가치가 있다. 아래 활용은 P0 완료 사실이 아니라 후속 검토 후보다.

| 영역 | 활용 | 경계 |
| --- | --- | --- |
| 입력 | 사용자가 넣은 폰트의 첫닿·홀자·받침 배치 특성을 읽어 구조 요약과 시작 후보 제공 | 외부 윤곽을 자모 마스터로 복사하지 않음 |
| 생성 엔진 | 여러 검증 폰트에서 반복되는 문맥 차이로 `LayoutProfile`·`ContextPreset` 후보 제안 | 한 폰트 관측값을 기본 프리셋으로 자동 승격하지 않음 |
| 생성 엔진 | 기둥·보와 이웃 자소 사이 거리 분포로 충돌 회피·최소 여백 기준 보정 | 광학 보정과 구조 충돌을 같은 규칙으로 합치지 않음 |
| 편집 | 완성 글자에서 `기둥`, `윗 보`, `아랫 보` 같은 역할을 선택하고 관련 자모·문맥 편집 범위 제안 | 사용자가 적용 범위를 확인한 뒤 전파 |
| 편집 | 현재 만든 글자의 역할선을 검증 폰트 분포와 비교해 과도한 치우침·길이·간격 경고 | 정답 강제 대신 비교 근거와 되돌리기 제공 |
| 출력 | 11,172자 전체 생성 뒤 기준선·간격·문맥별 이상치를 자동 탐지하는 preflight QA | 정상 범위 밖 결과를 자동 수정하지 않음 |
| 출력 | 제공 프리셋마다 근거 폰트·파일 SHA·분포·사용자 승인 이력을 남겨 재현 가능한 버전 관리 | 출처·라이선스·분석값과 생산값을 분리 |
| 공통 기반 | 추출기와 렌더러 변경 때 구조 회귀를 잡는 gold·holdout 데이터셋 | 사용자 승인 없는 후보를 gold로 사용하지 않음 |

우선 활용 순서는 `프리셋 근거 → 출력 QA → 편집 가이드 → 역할 기반 일괄 편집 → 외부 폰트 시작 후보`다. 앞쪽 두 항목은 관측값을 읽기만 하므로 생산 데이터를 바꾸지 않고 먼저 검증할 수 있다.

프리셋은 특정 외부 폰트 한 개의 좌표를 옮기는 방식으로 만들지 않는다. 여러 적법한 분석 대상에서 반복되는 비율과 문맥 차이를 후보로 만들고, 실제 앱 글자로 비교한 뒤 사용자가 고른 값만 별도 생산 fixture로 승격한다.

## 폰트 재구성 가능성의 경계

홀자 기준선 P0의 정보만으로 Noto Sans KR을 다시 만들 수는 없다. 현재 값은 완성 윤곽에서 일부 역할 면의 위치를 읽은 손실 관측값이다. 같은 기준선을 만족하는 획 모양·굵기·곡률·끝처리·접합 방식은 여러 개일 수 있다.

후속 원자화가 아래 정보까지 포함하면 Noto Sans KR과 비슷한 한글 생성 문법을 역으로 구성할 수 있다는 가설은 성립한다.

- 전체 자모의 획·면 윤곽과 위상, 속공간
- 획 굵기 프로필, 곡률, 결합부, 끝처리
- 초성·중성·종성 역할별 마스터와 반복 부품 관계
- 조합 문맥별 배치·변형 규칙과 글리프별 예외
- advance, baseline, side bearing을 포함한 출력 메트릭

원본과 정확히 같은 폰트를 재현하려면 모든 예외와 잔차까지 무손실로 보존해야 한다. 잔차가 글리프마다 원본 윤곽에 가까워지면 이는 생성 문법 추출보다 윤곽 재저장에 가깝다. 제품 목표 후보는 특정 폰트 복제가 아니라 `외부 폰트 → 편집 가능한 생성 문법 → 보지 않은 글리프 재구성`으로 둔다.

검증은 학습에 쓰지 않은 완성 글자를 재생성해 원본과 비교하는 holdout reconstruction으로 한다. 역할선·ink bounds·속공간·윤곽 거리·조판 메트릭을 따로 측정해야 기준선만 맞고 형태는 다른 실패를 잡을 수 있다. 이 방향은 P0 완료 뒤 별도 승인 단위로 검토하며, P0 추출 결과를 생산 자모나 외부 폰트 복제 데이터로 자동 승격하지 않는다.

## 완료 정의

- D0 문서 책임과 서버 단일 구현 경로가 유지됨.
- G0–G4 기록과 수치 결과가 남음.
- 정확도 통과 기준 충족.
- 직접 입력한 runtime 후보 없이 선택한 글자에서 후보 또는 자동 포기가 결정적으로 계산됨.
- 같은 입력은 캐시 유무와 관계없이 같은 결과를 냄.
- 후보가 생산 설계값으로 자동 승격되는 경로 없음.
- build·lint·관련 unit·E2E 통과.
- 확대 범위는 자동 진행하지 않고 사용자 판단으로 `진행·보류`를 기록함.
